# Walk SwiftUI 编写标准

## 范围与权威

本标准定义 Walk iOS 的 View／State 职责拆分和公共基础层复用方式，是已批准的平台编写标准，不是 Apple 强制要求的架构，也不代表现有实现已经全部符合。

本文件由 [iOS 平台规范入口](./README.md)统一索引，并细化其中的 R-DEP 职责边界。产品、业务行为、Data、API 与 UI 事实仍以入口列出的上游权威为准；本标准不新增或修改这些合同，不以客户端状态类型创造新的业务阶段或可见状态。

标准适用于新建及按批准范围调整的对象。存量代码迁移单独批准和验证；制定标准不授权批量重构、修改构建配置或替换状态观察机制。

## View／State 拆分

### 职责边界

View 描述界面，State 描述当前状态，ViewModel 管理页面流程，Service 提供业务数据操作。

View 负责组件组合、布局、状态展示、局部交互和事件转发。允许在生命周期入口触发加载、在按钮回调中调用模型方法，以及根据明确结果消费导航动作合同或执行合同允许的关闭。页面只表达导航意图，全局导航和跨域流程协调仍由 App 负责；View 不接管全局导航栈，不负责串联业务请求、解释服务端错误或维护业务状态转换。`body` 和初始化过程不得发起请求或产生业务副作用。

State 使用 `struct` 或 `enum` 表达页面需要呈现的数据、阶段、草稿和操作状态。它不包含 View、Service、网络请求或任务句柄，不自行加载和保存数据。纯计算属性可以属于 State，例如输入是否有效、草稿是否改变；相关判定必须遵循上游合同。自定义 State 类型是状态数据结构，SwiftUI 的 `@State` 是存储管理机制，两者不等同。

ViewModel 负责持有页面状态、处理用户操作、调用注入的 Service、执行校验和更新状态。它不生成 SwiftUI View，不持有页面壳，不直接操纵全局导航。业务资格、错误语义和状态流转引用上游合同，不能在模型中另定一套。

Service 不承担页面展示状态，也不依赖 View 或 ViewModel；其依赖边界遵循平台入口的 R-DEP。

### 哪些对象需要拆分

纯展示组件、简单控件和布局子视图不创建 ViewModel。

具有业务数据加载、保存、重试或多步骤编辑流程的页面，应有明确的页面模型。页面可以消费上层持有的共享模型，不要求每个 View 都新建一个模型。

存在互斥阶段、字段联动或需要整体转换的状态时，应显式定义页面 State。独立加载分区可以各自表达状态，不必合并为一个全页状态机。仅字段多，不构成拆分理由；简单页面可以直接使用模型中的少量状态属性，不为凑齐三个文件创建空 State。

复杂表单的草稿、校验、修改判断和提交状态必须由同一个页面模型管理。不能把草稿和校验放在 View，把提交阶段放在模型，再靠双方维护的标志拼出完整流程。

### 状态所有权与修改入口

每份状态只有一个所有者。页面私有状态由页面持有；多个页面共同使用且需要保持一致的状态，由生命周期合适的共同上层持有并注入。消费方不得复制共享状态后依靠监听反复同步。

展开、选中、滚动位置等局部 UI 状态可以留在所属 View，通常使用 `@State`；输入控件焦点使用 `@FocusState`。编辑草稿可以从业务数据初始化，但必须明确何时初始化、何时提交、何时丢弃，不能与原始数据双向自动覆盖。

业务数据、请求阶段和操作结果对 View 只读，由模型的方法修改。输入控件允许使用字段级 Binding；涉及校验或状态联动时，Binding 的写入必须经过模型更新方法。不得把完整页面 State 暴露为任意可写对象。

保存、删除等调用应向调用者提供可明确判断的本次结果，或者由明确的操作状态表达。不得依赖可被其他操作覆盖的全局 `lastMutationSucceeded` 一类标志判断本次操作是否成功。

### 状态表达与异步操作

互斥阶段使用枚举表达，不使用多个布尔值组合出可能矛盾的状态。独立分区分别表达状态，不因为某一区域加载而强制整页进入 loading。

可由已有数据计算出的内容不重复存储。页面 State 是可变状态的来源，组件 Projection 是从中生成的展示输入，不维护第二份可写事实。

是否保留刷新前内容、错误替换范围和重试行为，引用既有业务与 UI 合同；其中状态替换范围见 [App Structure](../../docs/ui/app-structure.md) 的「状态替换」。通用状态类型不得自行统一这些业务语义。

与页面显示相关的加载由 `.task` 等生命周期入口触发。模型必须明确重复调用、取消和迟到结果的处理方式；不能假设任务被取消后，所有异步工作都会自动停止。UI 状态更新在主 Actor 上完成，耗时同步工作不得堵塞主 Actor。

### 文件组织与组件边界

复杂页面的 `XxxView.swift`、`XxxState.swift`、`XxxViewModel.swift` 放在所属业务目录中，按页面任务共置，不另建全局 Views、States、ViewModels 大目录。小型私有辅助类型可以留在所属文件，不按行数机械拆分。

组件身份和输入、事件边界遵循 [UI Taxonomy](../../docs/ui/taxonomy.md) 的「组件资格总判据」「组合组件 vs Page 非组件的硬测试」与「逻辑合同强制化」。在 SwiftUI 中，业务组件以自身 Projection 和明确事件回调承接该合同，只持有合同允许的局部 UI 状态，不接收整个页面 ViewModel，也不自行请求业务数据。Projection 与组件生产实现共置。

单纯为排列、滚动或装饰抽出的子 View 仍是内部节点，不因拆文件就成为独立 Component；是否建立组件身份由上述总规范决定。

## 公共基础层

### 采用组合，不建立万能基类

不建立强制所有对象继承的 `BaseView`、`BaseViewModel`、`BaseState`。不为统一名称而添加空协议，也不创建包含加载、错误、导航、弹窗和请求的万能模型。

公共结构使用页面壳，公共外观和局部行为使用 Modifier 或 Style，重复的业务能力通过明确依赖复用。只有存在真实共同调用契约时才抽协议。

通用状态类型只能提取已经一致的语义，不能把不同页面的加载、刷新和错误行为强行统一。

### 页面壳的职责

页面按平台入口中的 Page／Component 映射使用已有页面壳及已批准的独立承载方式，不要求所有页面套同一个壳。

壳的结构、插槽和滚动、安全区、固定区域所有权，引用 [App Structure](../../docs/ui/app-structure.md) 与 [utility-page](../../docs/ui/components/common/utility-page/spec.md) 等对应 Component 合同。iOS 页面壳按合同承担 UI 组装，不负责业务加载、登录判断、保存或业务错误解释。

Page 只消费合同已有的插槽，不在页面中复制壳内部结构。滚动拥有者及分页嵌套例外遵循 App Structure，不由各页面自行扩展。缺少插槽或承载能力时，回到对应规范提出变更，不在页面中绕过。

### 统一状态观察机制

新建及完成迁移对象统一采用 Observation：页面模型使用 `@MainActor @Observable final class`；视图拥有模型时使用 `@State`，消费已有模型时使用普通属性或 `@Environment`，需要属性绑定时使用 `@Bindable`。使用 `@Bindable` 不改变前述只读状态和字段级修改入口约束。

既有 `ObservableObject` 属于迁移前实现，仍按 `@StateObject` 持有、`@ObservedObject` 消费。迁移单独批准和验证，不在制定本标准时批量替换，不为同一对象维护两套实现。

Apple 的 [UI 状态管理](https://developer.apple.com/documentation/swiftui/managing-user-interface-state)、[模型数据管理](https://developer.apple.com/documentation/swiftui/managing-model-data-in-your-app)、[Observation 迁移说明](https://developer.apple.com/documentation/swiftui/migrating-from-the-observable-object-protocol-to-the-observable-macro)与[自定义 View 说明](https://developer.apple.com/documentation/swiftui/declaring-a-custom-view)提供 API 与组合方式依据；页面模型命名、State 拆分条件和目录规则属于本项目的编写约定，不宣称为 Apple 强制架构。

## 验收口径

审阅一个页面时，应能明确回答：状态由谁持有、哪些入口可以修改、业务操作在哪里执行、子组件依赖什么、公共壳负责到哪里。任何一项必须通过追踪多个零散标志才能回答，都应重新检查边界。

模型测试验证状态转换、校验、失败、取消和适用的迟到结果处理。组件交互通过 UITest 验证，手工体验进入 DebugPanel；具体承载及生产实现共用要求引用平台入口的「组件测试与手动预览」，不建立预览专用替代实现。

现有模块依赖与平台登记测试不等于本标准全部职责已受自动检查。实施符合性应结合生产调用链审阅与受影响测试确认；规范落地、构建通过和业务端到端验收是不同层级的证据，不互相替代。
